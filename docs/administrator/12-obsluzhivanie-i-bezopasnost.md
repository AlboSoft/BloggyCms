## Резервные копии

Правило: **три вещи, которые нужно сохранять** — база данных, папка `uploads/` и файлы конфигурации (`system/config/config.php`, `database.php`).

```bash
# База данных
mysqldump -u bloggy -p bloggycms > bloggycms-$(date +%F).sql

# Пользовательские файлы и конфигурация
tar -czf bloggy-files-$(date +%F).tar.gz uploads system/config
```

**Как часто:**

| Тип сайта | База | Файлы |
|---|---|---|
| Личный блог, публикации раз в неделю | ежедневно | раз в неделю |
| Активный проект с комментариями | каждые 6–12 часов | раз в неделю |
| Магазин/портал с заказами | ежедневно + перед обновлениями | ежедневно |

> [!TIP]
> Храните копии **вне сервера**: на домашнем диске, в облаке, на отдельном хостинге. Бэкап, лежащий рядом с сайтом, не спасёт при потере хостинга, но спасёт от ошибки в базе.

**Восстановление:**

```bash
mysql -u bloggy -p bloggycms < bloggycms-2026-05-05.sql
tar -xzf bloggy-files-2026-05-05.tar.gz -C /путь/к/сайту
```

После восстановления очистите кеш: **Контент-блоки → Очистить кеш блоков** и **SEO → Очистить кеш SEO**.

## Права на файлы

Рекомендуемая схема для Apache/Nginx + PHP-FPM:

| Путь | Права | Комментарий |
|---|---|---|
| Корень сайта, файлы | `644` | Чтение всем, запись владельцу |
| Каталоги | `755` | |
| `uploads/` | `755` (или `775`, если группа веб-сервера) | Веб-сервер должен писать |
| `system/config/` | `755` | Сюда пишутся `config.php` и `database.php` |
| `templates/` | `755` | Нужна запись для редактора шаблонов и бэкапов |
| `system/logs/`, `cache/` | `755` | Логи и кеш |

```bash
chmod -R 755 uploads system/config templates
chmod -R 644 index.php
```

> [!WARNING]
> Не выставляйте `777` «чтобы работало». Если без этого не работает — проблема в том, что PHP и владелец файлов это разные пользователи; решите это настройкой хостинга или группы.

Закройте от доступа извне:

```nginx
location ^~ /system/ { deny all; }
location ^~ /cache/  { deny all; }
```

В Apache это уже сделано в поставляемом `.htaccess`.

## Журналы и диагностика

| Источник | Где смотреть |
|---|---|
| Ошибки движка | `/admin/debug` (включается `debug_mode`) |
| Логи PHP и веб-сервера | Логи хостинга (`error_log`), `system/logs/` |
| Журнал приложения | `Logger`, уровень задаётся `log_level` |
| Что пишут пользователи | `/admin/search-history` — популярные поисковые запросы |
| Активность пользователей | Профиль → сессии, таблица `user_activity` |

Фильтры в `/admin/debug` позволяют отметить ошибку как исправленную, посмотреть статистику и почистить журнал.

**Типовые симптомы:**

| Симптом | Причина и решение |
|---|---|
| Белый экран | Ошибка PHP. Временно включите `debug_mode`, посмотрите `/admin/debug` и лог сервера |
| «Доступ запрещён» при сохранении файлов темы | Нет прав на запись в `templates/` |
| Не обновляется sitemap | Нет прав на запись в корень сайта |
| Сайт тормозит после правок блоков | Очистите кеш блоков (`/admin/html-blocks/clear-cache`) |
| Поиск не находит новые посты | Пост в черновике либо кеш поиска; проверьте статус |
| Письма не приходят | Проверьте почтовый сервер хостинга и `contact_email` |
| Старые мета-теги на сайте | Очистите кеш SEO (`/admin/seo/clear-cache`) |
| 404 на всех страницах | Не работает `mod_rewrite`/`try_files`, проверьте `.htaccess` или конфиг Nginx |

## Обновление PHP и зависимостей сервера

- Минимум для движка — **PHP 8.0**, рекомендуем **8.3+**.
- Обновление минорной версии PHP (8.2 → 8.3) обычно безопасно, но проверяйте сайт сразу после: логи, формы, загрузку файлов.
- Сторонние библиотеки движка (Bootstrap, jQuery, иконки) лежат внутри темы — обновлять их вручную нужно редко и осторожно, чтобы не задеть вёрстку.

## Безопасность: что уже сделано движком

| Механизм | Где |
|---|---|
| CSRF-токены для форм | `CsrfToken`, `AdminForm` |
| Проверка прав по группам | `PermissionManager`, `AuthHelper::can()` |
| Защита админки middleware | `AdminAuthMiddleware` |
| Ограничение попыток входа, блокировка IP | `login_attempts` |
| Капча: математика, текст, картинка, honeypot | `CaptchaHelper` |
| Проверка загружаемых файлов | `FileUpload`, `FilesUpload` |
| Экранирование вывода | хелпер `html()` |
| Защита служебных директорий | `.htaccess` / рекомендованный Nginx-конфиг |

**Что остаётся на вас:**

- сложные пароли и их смена;
- своевременное обновление движка;
- аккуратность с пакетами дополнений (они выполняют код на вашем сервере);
- ограничение доступа к базе данных и панели хостинга.

## Что делать при подозрении на взлом

1. **Смените пароли** администраторов и доступ к базе.
2. **Проверьте пользователей** с флагом `is_admin` — не появился ли лишний.
3. **Проверьте файлы** в `uploads/` и корне на незнакомый код (особенно `.php` в местах, где их быть не должно).
4. **Посмотрите `debug_logs`** и логи сервера за последние дни.
5. **Восстановите** сайт из бэкапа, если изменения нашли, и закройте уязвимость (обновите движок).
6. **Настройте** резервные копии по расписанию, если их не было.
